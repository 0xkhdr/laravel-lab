# Pillar / Catalog / Foundry workspace

PHP **8.4**, Laravel **12**, SQLite and a private Redis service. The reference repository is mounted read-only; it supplies no vendor files, credentials or data. This is a local prototype, not a published release.

## Intent and architecture

This workspace proves the Raid Laravel ecosystem in independent applications: reusable runtime foundations provide behavior, application modules customize it, and development tooling assembles integration safely. The digital-card reference supplies use cases, not a requirement to reproduce the entire application. **Catalog is the only supported slice.**

| Layer | Responsibility |
| --- | --- |
| Laravel | Container, Eloquent, HTTP, queues, events and framework lifecycle |
| [Pillar](packages/pillar/README.md) | Action execution, repository/cache behavior and retained module conventions |
| [Catalog](packages/catalog/README.md) | Portable Catalog models, actions, permission states and schema templates |
| Application modules | Routes, requests/resources, authorization, user integration and project rules |
| [Foundry](packages/foundry/README.md) | Development-time Catalog planning, generation, registration and file recovery |

Runtime packages and generated modules never import Foundry. Composer installs dependencies; Foundry configures already-installed packages, not databases. The local packages are unpublished. This is not full reference-app parity: the generated module has four CRUD adapters and read/write gates, not permission-management HTTP endpoints, fine-grained Spatie RBAC, user-type middleware or idempotency.

## Docker bootstrap

```sh
docker compose build app
# New checkout only:
cp consumer/.env.example consumer/.env
docker compose up -d app redis
docker compose exec -T app composer install --no-interaction
docker compose exec -T app php -r "file_exists('database/database.sqlite') || touch('database/database.sqlite');"
# New checkout only; preserve existing application keys:
docker compose exec -T app php artisan key:generate
docker compose up -d web
docker compose exec -T app php artisan test --compact
docker compose exec -T -w /workspace/packages/pillar app composer install --no-interaction
docker compose exec -T -w /workspace/packages/pillar app vendor/bin/pest
docker compose exec -T -w /workspace/packages/catalog app composer install --no-interaction
docker compose exec -T -w /workspace/packages/catalog app vendor/bin/pest
docker compose exec -T -w /workspace/packages/foundry app composer install --no-interaction
docker compose exec -T -w /workspace/packages/foundry app vendor/bin/pest
```

Open http://localhost:8088. The web service binds only to localhost; set WEB_PORT to change the host port and update the consumer APP_URL accordingly. It uses Laravel’s development server. Start app/redis and install dependencies before starting web. File sessions and synchronous queues let the sandbox boot before database migrations. Catalog database operations still require an explicit operator migration step. Existing generated development keys are untracked. Composer cache/home are workspace-private. Set LOCAL_UID/LOCAL_GID when the host user differs from 1000.

- `packages/pillar`: runtime architecture and retained module discovery.
- `packages/catalog`: generic translated Catalog and explicit permission states.
- `packages/foundry`: development-only Catalog installation/scaffolding.
- `consumer`: primary development sandbox; supplied SKU behavior.
- `consumer-example`: acceptance fixture with independent vendor/lock/database/cache; custom uppercase SKU policy and no Foundry dependency.
- `consumer-foundry`: disposable Foundry installation acceptance fixture, already generated in this checkout.
- `build/consumer`: ignored, disposable production and upgrade fixture; regenerated by the evidence tooling.

Foundry interfaces are implemented, limited to `catalog.standard`:

```sh
docker compose exec -T app php artisan foundry:install --dry-run --no-interaction
docker compose exec -T app php artisan foundry:add catalog --dry-run --no-interaction
docker compose exec -T app php artisan foundry:add catalog --no-interaction
docker compose exec -T app composer dump-autoload --no-interaction
docker compose exec -T app php artisan foundry:doctor --no-interaction
```

`install`, `add catalog` and `make-module Catalog` reconcile the same integration, so they do not create parallel modules. Migrations are a **separate operator step**, never executed by Foundry. A fresh Laravel application must explicitly supply compatible application-owned UUID users, the `is_catalog_admin` field, and Sanctum token schema with UUID morph keys before using the recipe. The consumers provide these migrations; Foundry does not infer or rewrite arbitrary identity schemas. Its prerequisite inspection is heuristic, not proof of compatibility.

Source package names/namespace compatibility, public vendor ownership and any production-data migration require separate release work. No Wallet, Webhooks, billing, media, or absent starter capabilities are advertised.

## Package ownership and versions

Edit package code only under `packages/`. Consumer `vendor/raid/` entries are Composer-managed symlinks to these sources. `build/packages/` contains disposable release copies; never edit them for development. Use the primary sandbox for daily work and retain the other consumers for acceptance checks.

Pillar and Catalog are runtime dependencies. Foundry is a development dependency and must be absent from production `--no-dev` installs. Generated code under `consumer/app-modules/catalog/` is application-owned; customization belongs there.

`dev-main` identifies local development packages. Release fixture labels `0.1.0` and `0.1.1` test upgrades and are not published versions. Foundry recipe/blueprint `1.1.0` versions generated templates separately from Composer packages.

Consumer Composer setup and creation hooks do not run migrations. Do not use `composer setup` for the Docker bootstrap: its inherited frontend steps require Node, which the PHP image does not include. Use the commands above. Historical scripts under `tools/` reconstruct acceptance evidence; they are not the normal development entry point.

Catalog shared-file recovery and the application-owned authentication/authorization contract are documented in [Foundry README](packages/foundry/README.md). Identity remains future preparation; Catalog is the only supported recipe.

## Development cycle

1. Read the relevant package contract and [current plan](PLAN.md); edit authoritative package sources or application-owned integration, not vendor/release copies.
2. Add focused behavior coverage for the changed contract. Run Composer, Artisan, Pest/PHPUnit and Laravel-preset Pint inside Docker; new PHP requires explicit strict types.
3. Run affected package suites and downstream Catalog/consumer checks using the bootstrap command pattern. Use real Redis for cache claims; select other consumer fixtures when customization or generated integration changes.
4. For Foundry changes, verify write-free preview, unchanged reruns, conflicts and file recovery. After apply/recovery, explicitly refresh Composer autoload, clear application caches and run doctor in a new process. Never use file recovery as database rollback.
5. Record actual results and recovery boundaries in [IMPLEMENTATION.md](IMPLEMENTATION.md). Rebuild disposable production/upgrade evidence when affected; do not present old counts as a fresh baseline.
