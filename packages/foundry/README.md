# raid/foundry

Development tooling for PHP 8.4 / Laravel 12. Install with Composer as a development dependency. Runtime dependencies are Laravel, Pillar and Composer runtime metadata; Catalog/Sanctum are explicit integration prerequisites, installed separately by the consumer. Generated modules declare their own runtime dependencies.

Implemented interfaces:

- `foundry:install [--module=Catalog] [--dry-run]`
- `foundry:add catalog [--module=Catalog] [--dry-run]`
- `foundry:make-module Catalog [--blueprint=catalog.standard] [--dry-run]`
- `foundry:doctor [--module=Catalog]`
- `foundry:rollback [--module=Catalog]` (files only)

Only Catalog is supported. Module names and configured app-modules paths/namespaces are validated; escaping paths and symlink destinations fail. Existing installed versions, authentication schema prerequisites, syntax, duplicate schema identities and registration anchors are inspected before mutations. Unknown PHP layouts receive a manual registration patch rather than a guessed edit. Composer performs installation/autoload generation; Foundry never runs Composer or migrations.

Plans contain recipe/blueprint versions, prerequisites, exact relative paths, expected/desired SHA-256 hashes, ownership, conflicts, verification and a separate migration report. Customized files are preserved with nonzero results and proposed content for review. The current blueprint v1.1.0 supplies four CRUD adapters, bearer-token auth integration, the SKU hook, user permission adapter and meaningful application tests.

Apply uses an exclusive lock, atomic file replacement and `.foundry/installations.json`. Each stable operation ID records before/desired/completed hashes, template identity and status. A checkpoint follows output verification; a process exit after writing but before its checkpoint leaves a pending record. Retry checks existing output hashes and resumes without duplicate migration identities. Successful identical reruns leave files and journal unchanged.

Generated files retain whole-file hash protection. For shared `composer.json` and `bootstrap/providers.php`, Foundry owns only its exact PSR-4 mapping and provider-array entry. Additional mappings/providers, Composer settings and PHP comments remain application-owned. Reconciliation accepts these additions; changed Catalog mappings, duplicate providers, missing completed registrations and unsupported PHP layouts produce reviewable conflicts. PHP is tokenized, never executed: supported layouts are a literal returned class array, optional strict-types declaration, simple imports/aliases and comments. Dynamic expressions, grouped imports and comments inside Catalog's class expression need manual review. New registrations use absolute class names so unrelated imports cannot redirect them.

Journal schema remains **1**, with additive per-operation `contribution.version = 1`, expected key/value, ownership and original output hash. Stable path SHA-256 operation IDs, template identities and `installations.catalog` remain unchanged. Legacy operations without contribution metadata infer ownership from their hash-verified original backup (or an unchanged before-file for an operation not yet written); identical before/planned hashes mean an adopted registration. Unprovable legacy ownership stops preview/apply/recovery with the file and journal identified. Preview never converts the journal; apply checkpoints metadata once, then identical reruns remain unchanged. Unknown journal/contribution versions stop safely. Use this Foundry version for subsequent recovery; older tooling does not understand contribution ownership.

Recovery preflights every output under the lock, then removes only Catalog's owned, unchanged registration. Already absent contributions are safe no-ops when resuming recovery; preexisting adopted registrations stay. A verified original backup restores exact formatting only when the current bytes still match the original output hash. After any later edit, recovery patches the current content instead: PHP bytes outside the removed registration remain intact; Composer JSON retains unrelated values/object types but may be reformatted. Modern contribution recovery can work without a backup; legacy ownership inference and generated-file restoration still require verified backup evidence when the before-file is unavailable. Changed mappings, ambiguous layouts and customized generated files stop recovery before application writes. Recovery rechecks each destination hash before mutation, checkpoints restored operations and can resume after a write before its checkpoint. This is **not database rollback**. After any separately executed database migration, review database recovery independently; do not remove applied migration history as an upgrade mechanism. Runtime/schema upgrades require new migration identities and reviewed application changes, never timestamp regeneration of an old template.

After an apply or file recovery, run `composer dump-autoload`, clear application caches, then run doctor in a new process. Generated code is application-owned and contains no Foundry imports. Production `composer install --no-dev` must exclude this package. No optional Media/Wallet/Webhooks integrations or generic generator catalog are supplied.

Run `composer install` and `vendor/bin/pest` inside this package's Docker directory. The suite includes write-free preview, conflicts/preflight, custom layouts, stale plans, deterministic migration IDs, interruption/resume, versioned blueprint upgrades and file restoration.


## Catalog authentication and authorization contract

The application is the integration owner. The current Catalog blueprint is a concrete Sanctum/UUID adapter, not a portable Identity installer. A future Identity foundation is recommended, but is not implemented or required by Catalog runtime.

- **Schema owner:** one application module owns `users`, UUID identifiers, the current `is_catalog_admin` policy field and Sanctum `personal_access_tokens` with UUID morph keys. Catalog owns only its Catalog tables/migration identities. A future Identity integration must adopt the existing users/token schema through a reviewed compatibility transition; never generate competing tables/migrations. Foundry's prerequisite inspection is a heuristic, not proof of schema compatibility. Migration/data execution remains an explicit operator action.
- **Model and guard owner:** the application chooses one authenticatable model and configures Laravel's user provider, authentication guards, Sanctum and `catalog.user_model` / `catalog.auth_guard` consistently. Today generated `CatalogUser` extends `App\Models\User` and supplies UUID, Sanctum and Catalog permission traits; its provider explicitly sets the users model and Catalog's guard to Sanctum. These are application-owned choices. A future Identity integration must replace/adapt this wiring deliberately, including the generated gate callback types and `auth:sanctum` routes. Competing providers must not silently overwrite model/guard configuration based on boot order. Catalog runtime neither owns the users model nor issues/revokes tokens; Foundry is absent from runtime.
- **Endpoint authorization:** application middleware authenticates requests and application gates decide `catalog.read` / `catalog.write`. Current read gate permits an authenticated `CatalogUser`; write gate requires its administrator flag. The application owns any later RBAC/ability policy. Catalog actions do not provide a general HTTP/mutation authorization boundary; non-HTTP callers must authorize explicitly. Token abilities are not implicitly Catalog permissions.
- **Row visibility:** Catalog's read scopes separately enforce explicit permission states and brand/category/product union grants. Endpoint access and administrator status do not imply unrestricted row visibility. Grant `Unrestricted` explicitly when policy requires it; missing/unconfigured state, guests, missing/malformed permission adapters, missing inheritance parents and cycles deny visible rows. Regions currently have no row permission filter; their HTTP access still requires the endpoint gates. Permission-management HTTP endpoints are not part of this blueprint.
- **Revocation:** revoked/deleted Sanctum tokens must fail authentication on the next bearer-only request. Permission revocation must remove previously cached row access, including inherited access; use Catalog permission actions and their transaction/after-commit invalidation rather than raw table writes that bypass invalidation. A future Identity adapter must preserve both guarantees and user-isolated cache behavior. Integration acceptance must exercise guest/client/admin endpoint denial, missing/malformed adapters, explicit unrestricted/restricted/denied states, cached grant revocation and actual token deletion.

Existing Catalog package tests prove missing-adapter denial, explicit states, inherited revocation and Redis cache isolation/revocation; consumer HTTP tests prove endpoint denial and actual Sanctum token revocation. Any future Identity transition must rerun and extend these contracts before changing generated wiring.
